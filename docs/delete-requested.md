# 서버 삭제 요청 추적

서버 삭제 API가 성공을 응답해도 서버가 NCP 목록에서 사라지는 데 시간이 걸릴 수 있다.
`DELETE_REQUESTED`는 **삭제 완료가 아니라 완료 확인 중**인 휴지통 상태다.
같은 자원에 삭제 API를 다시 보내지 않도록 요청 전 상태를 DB에 먼저 기록한다.

## 배포 순서

1. 팀장과 DB 백업 및 적용 시간을 정한다.
2. 기존 DB에는 `db/migrate-2026-10-13.sql`을 적용한다. 새 DB에는 변경된 `db/schema.sql`을 사용한다. `python -m db.init`만 다시 실행해도 기존 테이블은 변경되지 않는다.
3. 그다음 C 코드와 자동 작업을 배포한다. 마이그레이션 전 코드는 `delete_requested_at` 컬럼을 조회하므로 배포 순서를 바꾸면 안 된다.
4. 연습 모드에서 휴지통·화면·감시 테스트를 한 뒤 실제 삭제는 승인된 테스트 자원으로 별도 확인한다.

## 상태와 복구

- `WAITING`: 유예 기간 중. 기한이 오면 삭제 직전 안전 검사를 한다.
- `DELETE_REQUESTED`: 삭제 API를 보냈거나, 전송 직전 프로세스가 중단돼 전송 여부를 확인해야 한다. 다음 `run_purge`는 자원 목록만 다시 읽고 삭제 API를 호출하지 않는다.
- 목록에서 사라진 것이 확인되면 `PURGED`로 닫는다. 실행 중으로 다시 보이거나 60분 내 완료를 확인하지 못하면 `FAILED`로 남기고 수동 확인 알림을 보낸다.
- 삭제 요청 이력이 있는 `FAILED` 자원은 `top`에서 제외하고 새 `kill`도 거부한다. 관리자가 NCP 콘솔과 이벤트 기록을 확인하기 전에는 DB 상태를 임의로 초기화하지 않는다.
- `sudo kill -9`로 즉시 삭제하는 서버도 유예 기간은 건너뛰되 내부 휴지통에 요청 상태를 기록한다.
- 연습 모드에서는 삭제 API를 보내지 않는다. 앞서 실제로 요청한 항목의 소멸을 확인하는 작업은 계속할 수 있다.
